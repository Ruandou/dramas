# 7 阶段流水线全拆解：从 86 集大纲到成片

**开号时答应的这篇，今天交卷。001 结尾说「钱花在哪知道了，下一篇讲钱是怎么被一群 AI 岗位分工花出去的」，就是这一篇。**

先给结论：**七个阶段里，只有两个阶段花钱。**其余五个阶段从头到尾是纯文字工作，跑一整套 86 集的剧本，现金成本是 0。

## 一、七个阶段，七个岗位

我把流水线拆成七个阶段，每个阶段固定交给一个「岗位」，产出物是一份具体文件。阶段之间不靠模型记忆衔接，靠文件。这份文件就是下一个岗位的输入。

| 阶段 | 岗位 | 产出物 | 花钱吗 |
|---|---|---|---|
| ① 故事架构 | 大纲师 | 86 集大纲（含钩子位、情绪弧线） | 否 |
| ② 制片登记 | 制片登记 | 项目「宪法」+ 资产骨架卡（角色/场景/道具 ID） | 否 |
| ③ 视觉设计 | 道具师 → 角色师 / 场景师 | 参考图（含人脸网格变体） | 是 |
| ④ 分集编剧 | 编剧 | 逐集剧本 + 分镜脚本 | 否 |
| ⑤ 分镜构建 | 分镜构建师 | 机器可读的 shots / segments 配置 | 否 |
| ⑥ 视频生成 | 引擎执行 | 分集成片 mp4 | 是 |
| ⑦ 审查发布 | 总导演 | 标题/封面/简介合规确认 | 否 |

只有第 ③ 和第 ⑥ 阶段真开火：图片生成和视频生成。其余五个阶段烧的是对话订阅费，边际成本约等于 0。

019 说的《厂牌榜》002，提前到今天中午上线了，不是下周一。

## 二、两条轨道：一条零扣费，一条扣费

**七个阶段被分成两条独立推进的轨道，这是我踩坑最多才想明白的一层结构。**

剧本轨（①②④）不依赖任何付费接口，所以它可以连续跑。大纲写完直接写分集剧本，一集接一集，中间不必等任何一张图出好。这条轨道跑完一整套 86 集，账单一分钱不动。

制作轨（③⑤⑥）每一步都在扣费，所以它必须能停。视觉设计先出纯文字稿，我看完字再让它出图；图出完、传上对象存储拿到永久地址，才轮到第 ⑤ 阶段转配置、第 ⑥ 阶段出片。制作轨可以从任意一集单独启动，不必等剧本轨全部写完。

两条轨道唯一的交接点是一个状态标记：这一集剧本经审核定稿，就标成「可制作」，制作轨才认它。剧本轨继续往前走下一集，不等制作轨出片。这就是为什么我能在只有 6 部剧出成片的情况下，先攒下 1364 集的剧本。

## 三、岗位之间靠文件交接，不靠模型记忆

大模型没有跨会话记忆，所以「岗位协作出错」几乎从来不是模型答错，而是交接的文件没写清楚。

举一个真实的坑。第 ② 阶段会给每个角色、每个场景、每个道具发一个固定 ID，比如 `CHAR-007`、`SCENE-003`。第 ④ 阶段写剧本时如果引了一个还没登记过的路人，不能自己现编一个 ID，得用占位符标出来，交回第 ② 阶段补登记、第 ③ 阶段补图。我最早没定这条规矩，结果同一个路人被不同集数的剧本各自命名，第 ③ 阶段出了两张脸，跨集穿帮才发现，两张图白扣费。

同一类问题还有两条：画面里不许出现人脸，人脸由第 ⑥ 阶段的视频生成单独加，参考图里提前画了脸会串到成片；场景底图里不许放情节道具，放了就会被固化进底图，后面换一集它还穿着。这些都是交接文件必须写死的事。

## 四、每一步都有一道闸门

光有分工不够，还得有谁来验收。七个阶段之间插了六道闸门（G1 到 G6），加两道剧本审核（R1 大纲、R2 单集）。每道闸门只有两个结果：过，或者打回重做。

闸门不是走形式。举一条最贵的：单集剧本总时长必须在合规区间里，本号规格是 90 秒一集的竖屏短剧。如果不达标，唯一允许的做法是整集重写，禁止给某个镜头偷偷加几秒凑时长。原因是第 ⑥ 阶段按秒计费，剧本里多加 3 秒，视频就真拍满 3 秒，那是没人爱看、还实打实要付钱的钱。这条规矩是从账单上学来的。

R2 那道审核更狠一点：单集脚本低于分数线就打回改，直到审核方提的每一条问题都从剧本正文里改掉，才算干净放行；挂着问题往下游走是不行的。

## 五、这套结构现在跑到什么规模

今天在仓库里数了一遍，命令和结果都给你：

```
find dramas -maxdepth 2 -name "短剧剧本_*_*集.md" | wc -l   →  79
find dramas -type d -name "EP[0-9][0-9]" | wc -l             →  1364
find dramas -path "*/assets/looks/*.png" | wc -l             →  907
find dramas -path "*/assets/scenes/*.png" | wc -l            →  555
find dramas -path "*/assets/props/*.png" | wc -l             →  369
find dramas -name "*.mp4" | wc -l                            →  129
```

翻译一下：81 个项目、79 份 86 集大纲、61 个项目已经落到分集剧本、1364 集剧本目录、1831 张参考图（角色 907 / 场景 555 / 道具 369）、129 条成片 mp4（分布在 6 部剧里）。加上为绕过人脸过滤补出的 206 张网格变体，这些图全部是本地脚本和图片接口跑出来的。

这套结构现在的瓶颈不在剧本，也不在算力。**拦在「出片」这一下：1831 张图只换出 129 条成片。**换句话说，我把产量前移到了最便宜的那几个阶段，最贵的那一步还没加速。

## 六、一个人怎么用这套结构

如果你也在一个人做内容，这套分工能直接搬：

- 先立七份产出物，再谈模型。把七个阶段各自要交出什么文件写死，文件之间怎么引用（ID 怎么编、占位符怎么写）也写死。这一步不花钱，但决定了后面会不会重复扣费。
- 把付费阶段单独隔离成一条轨道。付费的动作（出图、出片）只在设计稿确认之后发生；设计稿是文字，改十遍不花钱。
- 每个付费阶段前放一道人工闸门。我做决策的点只有几个：大纲定不定、设计稿定不定、审核过不过。其余交给岗位跑，跑错由闸门拦。
- 先跑剧本轨，把它跑满。剧本轨零成本、可以连续推进，我现在的 1364 集就是这么攒的。等剧本轨够厚了，再拿最想验证的那一集去开制作轨。

**今天能做的**：拿你手上做得最熟的一件事，把它拆成「产出物 → 下一环的输入」的链条，找出哪几环在花钱。把花钱的环节圈出来，前后各加一道确认。这不是流程洁癖，是你唯一的成本控制点。

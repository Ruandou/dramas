### 9.2 排查顺序（从最可能到最费时间）

1. **个体户没有"法定代表人"，只有"经营者"**。表单在「企业」入口下把字段写成"法定代表人"，正确填法是执照上「经营者」本人的姓名 + 身份证号。若填了其他人（配偶/合伙人/代办人）→ 必然不一致。
2. **逐字核对**：姓名、身份证号、统一社会信用代码是否与执照完全一致（全半角括号、空格、末位 X 大小写）。
3. **拿硬证据**：在「国家企业信用信息公示系统」gsxt.gov.cn 按执照名称/统一社会信用代码查询，确认①已公示 ②经营状态"开业/存续" ③经营者姓名一致。
   - gsxt 查不到或信息不全 → **工商数据未同步到腾讯数据源**，新办个体户常见延迟数日至两周，只能等或改走对公打款。
   - gsxt 一切正常 → 属腾讯侧核验问题，走页面提示的「其他验证方式」。
4. **其他验证方式** = 通常为**对公账户打款验证**（向主体银行账户小额打款并回填金额）。需确认该个体户是否已开对公账户；没有则要么去开，要么回 1-3 找不一致原因。

## 0. 注册入口与额度（实测）

**正确入口**（三步向导：① 基本信息 → ② 信息登记 → ③ 公众号信息）：

```
https://mp.weixin.qq.com/cgi-bin/registermidpage?action=index&weblogo=1&lang=zh_CN
```

页面点「公众号」→ 弹窗「选择主体类型」→ 选**企业** → 确定，即进入第一步。

**额度规则（注册页原文）**：
> 个人可注册 1 个账号，个体工商户、企业、其他组织可注册 2 个账号，政府和媒体可注册 50 个账号。

选「企业」后的提示原文：
> 企业和个体工商户可注册 2 个账号。**请按照营业执照上的主体类型如实选择注册类型。**

→ 结论：**个体工商户走「企业」这个入口**，没有单独的「个体工商户」按钮；执照主体类型是个体工商户就如实填个体工商户。旧号「华华证件照」是个人主体，不占企业额度。

**两个易踩的坑（实测）**：
- ❌ `mp.weixin.qq.com/register` 和 `registerpage?action=show` 这两个 URL 都是 **404 空白页**，别用（我一开始给错了，已纠正）。
- 登录状态不影响注册向导，无需刻意开无痕窗口。但仍建议**用未登录过旧号的浏览器或无痕窗口**，避免混淆两个后台的登录态。

## 1. 第一步「基本信息」真实字段（照抄）

| 字段 | 要求（页面原文口径） |
|------|---------------------|
| 邮箱 | **作为登录账号**，须填写未被微信公众平台、微信开放平台、个人微信号绑定的邮箱 → 点「激活邮箱」收验证邮件，回填 6 位验证码 |
| 密码 | 字母、数字或英文符号，最短 8 位，**区分大小写**；需二次确认 |
| 注册地 | 选**中国大陆**。⚠️ 页面明示：非中国大陆的国家/地区**暂只支持申请企业类型服务号**（订阅号会走不通） |
| 协议 | 勾《微信公众平台服务协议》+《个人信息保护指引》后「下一步」才可点 |

> 邮箱是这一步唯一的硬门槛：一个邮箱只能绑一个平台账号。建议现注册一个专用新邮箱（163 或 Gmail），别用已被旧号占用的那个。

### 1.1 专用邮箱怎么取（163 实测，2026-09-28）

入口：`https://reg.163.com/reg0.shtml` → 三步：填写账号密码 → 验证手机号码 → 完成。

- 账号规则（页面常驻提示原文）：`账号请用字母、数字或下划线命名` → **点号不要用**；密码 8-16 位，需含大小写字母、数字、符号
- 后缀可选 `@163.com` / `@126.com` / `@yeah.net`，同一账号名可同时给出三个后缀
- 候选：账号名 = 号的拼音（`@163.com`），实际采用哪一个记在本地凭据文件里
- 注册需手机号 + 短信验证，**只能本人操作**；密码也不要交给助手代填
- ⚠️ **163 免费邮箱连续 90 天未登录会被冻结**（网易帮助中心官方口径，需通过 web 端 `mail.163.com` 登录自助解冻）。这个邮箱是公众号的**登录账号**，被冻结=账号进不去。对策二选一：① 手机日历设每月一次的登录提醒；② 改用自建域名邮箱或企业邮箱（更稳，但要花钱/要维护）
- 邮箱到手后**直接用于公众平台注册**，中途不要拿去绑个人微信、开放平台、小程序——一旦绑定就不满足「未被绑定的邮箱」要求

### 15.2 本轮新增的 B 级机制（后台自动化，全部实测）

1. **正文内插图走「合成 paste」，但必须先等 `selectionchange`**：`fetch('http://127.0.0.1:8766/x.png')` → `new File` → `DataTransfer.items.add` → 在目标 `<p>` 上 `Range` 设点 → **`await setTimeout(400~500)`** → 对该节点派发 `ClipboardEvent('paste',{clipboardData,bubbles,cancelable})`。同步派发不等同步 → ProseMirror 内部选区未更新，图片会被插到文档末尾。

### 16.3 正文插图定位：paste 前必须让 ProseMirror 拿到焦点

### 16.4 React 受控字段：赋值必须「置空 → 置值 → input」

- 摘要 `#js_description`、原创作者等字段，用 native setter 一次赋值后 **DOM 有值但计数器仍显示 `0/120` / `0/8`**，即组件 state 没同步，保存后会丢。
- 有效写法：`setter.call(el, '')` → dispatch `input` → 等 200–250ms → `setter.call(el, 正文)` → dispatch `input`（+`propertychange`/`keyup`/`change` 更稳）。做完计数器变 **101/120**、作者 **6/8** 才算写进去。
- **`fill` 工具按 uid 会命中同名隐藏字段**：本次 `fill` 摘要的 uid 实际写进了 `#title`（h=0 的隐藏 textarea），把标题污染成摘要文本；靠重新对标题 ProseMirror 做 `execCommand('delete')`+`insertText` 才同步回来。**标题/摘要这类"可见 PM + 隐藏 textarea 双控件"的字段，优先用 execCommand 或置空-置值法，别用 uid fill。**

### 17.4 本轮结论（标注证据等级）

1. **判据①成立：一天两篇不互相抢推荐**（B 级·实测，n=1 天，本号首次同日双发、无前例可比）。005 未群发却拿到首日 **69 人**、两日累计 **101 次**，渠道构成推荐 **95.7%**，与同日群发的 004（推荐 97.0%）同档 → 「同日第二篇走『发表·未群发』拿不到量」的悲观分支**证伪**。第二篇可常态化试，成本为零（不占通知额度）。仍不可外推：单账号、粉丝 4 人。
2. **判据②反转：字数拟合被证伪，选题才是主变量**（B 级）。004（4,299 字）与 005（4,044 字）长度接近、完读率**同为 17%**，而 §12 的单调负相关拟合在该长度区间预测约 25%–26%，实际低 8–9 个百分点；对照 003（3,905 字）29%、三角网格（3,024 字）35% → 差异落在**选题**上：广电规章解读类（004／005）明显低于「核数／账单／实操」类。→ §12 结论 1 的字数曲线**降级为 C 级观察**，不再用作预测；「结论和主数据落在前 300 字」这条保留（它与完读率的关系本轮未被检验）。
3. **群发买的是时序，不是总量**（B 级·新增观测，原判据未覆盖）。同口径对比（均取 `read_num` 次数，10-10 18:56 → 10-11 拉取）：004（群发）99 → **101，+2**；005（未群发）67 → **101，+34** → 群发的效果是**把阅读压进首日**（首日人数 004 **101 人** vs 005 **69 人**，此处 101 人为 detailpage 口径、与次数不同轴），但两天后累计 **101 : 101 打平**。次数序列的旁证：004 的累计次数已等于其首日人数 101 → 次日新增几乎为 0（次数 ≥ 人数，故只能取此方向）。同口径 003：首日 90 人、累计 102 次。→ 群发可量化收益修正为「首日时序 + 1 个新增关注」，累计阅读量不由通道决定。

### 22.2 后台自动化机制：本轮新增／更正 8 条（B 级，均为本轮一次通过或一次踩坑后复现）

1. **正文编辑器永远是 `.ProseMirror` 的 index 1**（index 0 是标题占位）。写校验脚本时别按"最后一个"取，页面下方还有隐藏的预览节点。
2. **导入的 md 必须带 cache-buster**：`fetch('http://127.0.0.1:8799/文章/009_发布版.md?cb='+Date.now(), {cache:'no-store'})`。不带 `?cb` 时 Chrome 会直接回缓存，**改完重导仍是旧内容**（本轮踩过一次：`**` 修好了但编辑器里星号数没变）。
3. **CommonMark 加粗闭合坑**（新发现，会漏裸星号进正文）：闭合 `**` 前面是**引号**、后面紧跟**非标点汉字**时不算闭合。本轮 009 的 `是**我这 12 条里唯一一条明确写到"竖屏"**的信息` 渲染出裸 `**`；改成 `是**我这 12 条里唯一一条**明确写到"竖屏"的信息` 即恢复。→ 发布前清单加一条固定动作：`grep` 两篇 md 里 `"[^"]*\*\*` 这类「引号紧邻闭合星号」的写法，并在编辑器里数 `innerText` 中 `**` 的个数必须为 **0**。
4. **正文插图必须拆成两次 `evaluate_script` 调用**（合并成一次会**静默失败**：`paste` 事件 `defaultPrevented=false`、不产生 `<img>`）。调用 A 只做选区（对目标 `<p>` 派发 `pointerdown`/`mousedown` → `range.selectNodeContents(p)` → `selection.addRange` → `document.dispatchEvent(new Event('selectionchange'))`）；调用 B 才做 `fetch` blob → `File` → `DataTransfer`（**`dt.items.add(file)` 不要传 mime 参数**）→ 两次 `selectionchange`（间隔 700ms／600ms）→ 对 `.ProseMirror` 派发 `ClipboardEvent('paste')`。**成功判据只看 `ev.defaultPrevented === true`**。多图按**从下往上**的顺序插，避免前面的插入使后面的锚点位移。

### 25.4 后台自动化机制：本轮新增／更正 8 条（B 级）

1. **🔴 正文粘贴上传有体积天花板**：`POST /cgi-bin/uploadimg2cdn` 对 **≈345 KB** 的 PNG 直接 `net::ERR_ABORTED`，控制台「图片粘贴上传失败: Error: Network Error during upload」→「超过绑定重试次数」，DOM 留 `paste_image_error_wrp` + `page_image_error data-reason="系统错误"`。**实测硬证据：187 KB 通过、345 KB 失败**（238–259 KB 未单测，本轮一并压缩求稳）。修法：`im.convert('RGB').quantize(colors=200, method=Image.MEDIANCUT, dither=Image.NONE).save(out, optimize=True)` → 88–129 KB，1080 宽下肉眼无差。**规则：配图上传前先看字节数，>200 KB 一律先出 `_q` 版**（原图仍留仓库作原图交付物）。
2. **删掉上传失败的图片节点：`execCommand('delete')`，不要用选中**。合成 `mousedown` 落点只会产生 `selType:"Caret"`，拿不到 ProseMirror 的 `NodeSelection`（`.ProseMirror-selectednode` 不出现）。可行做法：把折叠光标放到**图片后面那个空 `<p>` 开头**，`document.execCommand('delete')` 返回 true，PM 会响应用户输入并删掉前面的图片节点（本轮 41→40 节点、`blob:` 归零）。
3. **⚠️ 更正 §24.4-4（封面选择器）**：条目 class 的 ` selected` 与 `下一步.disabled` **两条都要看**，且**点缩略图是 toggle** —— 奇数次点中、偶数次取消。本轮反复点 CDP + 合成序列，选中态被自己抵消，误判成「点击无效」；截图上的绿框是**焦点**不是选中。稳定做法：**一次干净的 CDP `click`** → 立刻读 class 判定，不要补第二下。
4. **`#js_cover_area`／`#js_cover_null` 判封面状态是假阴性**：封面已裁好并生效后，这两个探针仍读不到内容。**封面状态只能用截图确认**（左侧卡片 + 右侧转发卡同时出现新图即成立）。
5. **草稿回读通道更正**：`appmsg?action=list_ex&begin=0&count=5&filter_type=101&type=101` 在**刚保存草稿后**返回 `base_resp.ret=0` 但 `app_msg_cnt=0`、`app_msg_list=[]` —— 它不是草稿箱接口，别拿它验 `copyright_type`。**要验草稿/成品状态直接查 `appmsgpublish`**（发表后），或用编辑器页内 `#author`／`#js_description`／设置区文本。
6. **`appmsgpublish` 的 nested `publish_info` 是时间戳真相源（新发现，比 §24 的取法更硬）**：`JSON.parse(publish_list[i].publish_info)` 里有 **`draft_msgid`（草稿↔成品官方绑定）、`create_time`（= 文章页 `var ct`，本轮逐秒对齐）、`update_time`、`publish_status`（200 已发表／300 已删除）**；`appmsg_info[0].delete_time` 直接给出删除时刻。→ 以后记账**不必**再抓文章页 HTML 取 `ct`，也不必用 `update_time` 反推删除时间。
7. **群发额度用尽后的发表是两段弹窗**：第一段（群发通知／定时发表两个开关，开关灰 + 文案「今天没有通知次数」）→ 点「发表」→ 第二段「**未开启群发通知**／内容将展示在公众号主页…」**按钮文案是「继续发表」**（不是「确定」）。之后才出「微信验证」二维码。
8. **扫码图最省事的取法**：`curl` 直接下 `safe/safeqrcode?ticket=…&uuid=…`（URL 整体加引号，含 `&`）→ 落地是 **300×300 的 JPEG**（扩展名写 .png 不影响扫码）。比 §23.5-8 的 canvas 二值化 + 本地 8766 服务更短；用完**立即删除**该文件（含会话 ticket，仓库是 public）。
